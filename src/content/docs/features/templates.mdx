SKIM uses raw PHP templates. No Twig, no Blade, no compilation step — real stack traces, IDE autocomplete, and opcache performance out of the box.

## File Layout

Templates live in `app/views/` and use the `.html` extension (preferred; `.php` is resolved as a fallback):

```
app/views/
  layouts/
    base.html
  pages/
    home.html
    dashboard.html
  components/
    alert.html
    card.html
```

## Rendering from a Controller

Always return a `Response` object. Never `echo` or `die`.

```php
use Skim\Core\Response;

class PostController {
    public function index(Response $res): Response {
        return $res->view('pages/home', ['title' => 'Welcome']);
    }

    public function show(Response $res, int $id): Response {
        $post = Post::findOrFail($id);
        return $res->view('pages/post', ['post' => $post]);
    }
}
```

## Layouts & Slots

A child template declares its layout and captures named slots. The layout renders afterwards and injects them.

**Child template** (`app/views/pages/home.html`):

```php
<?php $this->layout('layouts/base') ?>

<?php $this->start('title') ?>
    Home
<?php $this->end() ?>

<?php $this->start('content') ?>
    <h1>Welcome</h1>
    <p>Hello, <?= e($name) ?></p>
<?php $this->end() ?>
```

**Layout** (`app/views/layouts/base.html`):

```php
<!DOCTYPE html>
<html>
<head>
    <title><?= $this->slot('title', 'SKIM App') ?></title>
</head>
<body>
    <main><?= $this->slot('content') ?></main>
    <footer><?= $this->slot('footer', '&copy; 2026') ?></footer>
</body>
</html>
```

<Note>
`$this->slot()` returns a default value when the section was never captured. `$this->hasSection()` checks existence without defaults.
</Note>

<Warning>
Always call `e()` on user-supplied data. Skipping it is an XSS vulnerability.
</Warning>

### Aliases

`section()` and `endSection()` are aliases for `start()` and `end()`, and `block()` aliases `slot()`. Use whichever reads best — just don't mix both styles in the same file.

```php
<?php $this->section('content') ?>
    <p>Hello</p>
<?php $this->endSection() ?>
```

## Partials

Include a shared sub-template with `$this->include()` — the partial inherits the parent's data plus anything you pass explicitly:

```php
<?= $this->include('partials/errors', ['errors' => $errors]) ?>
```

## Components

Components are reusable, isolated templates that receive only their props. Parent data never leaks in.

### Array Props

```php
<?= component('alert', ['message' => 'Profile saved', 'type' => 'success']) ?>
```

### Readonly Props Objects (Recommended)

Define a `*Props` DTO class for type safety and IDE autocomplete — the class name must end in `Props`:

```php
// app/ViewProps/AlertProps.php
final readonly class AlertProps {
    public function __construct(
        public string $message,
        public string $type = 'info'
    ) {}
}
```

```php
<?= component('alert', new AlertProps(message: 'Profile saved', type: 'success')) ?>
```

**Component template** (`app/views/components/alert.html`):

```php
<div class="alert alert-<?= e($type) ?>">
    <?= e($message) ?>
</div>
```

<Note>
Anything not ending in `Props` throws a `ViewException`.
</Note>

### Components with Parts

When a component needs multiple named content blocks — like a card with an optional header and footer — use `componentWithParts()`:

```php
<?= componentWithParts('card', new CardProps(title: 'Profile'), function($c) { ?>
    <?php $c->part('header', function() { ?>
        <h2>Edit Profile</h2>
    <?php }) ?>

    <form>...</form>

    <?php $c->part('footer', function() { ?>
        <button>Save</button>
    <?php }) ?>
<?php }) ?>
```

**Component template** (`app/views/components/card.html`):

```php
<div class="card">
    <?php if (hasPart('header')): ?>
        <div class="card-header"><?= part('header') ?></div>
    <?php else: ?>
        <div class="card-header"><h3><?= e($title) ?></h3></div>
    <?php endif; ?>

    <div class="card-body"><?= part() ?></div>

    <?php if (hasPart('footer')): ?>
        <div class="card-footer"><?= part('footer') ?></div>
    <?php endif; ?>
</div>
```

The main body (anything outside `part()` calls) is available via `part()` with no arguments. Named parts use `part('name')` and `hasPart('name')`.

<Note>
`part()` and `hasPart()` read from a static stack, so nested components with parts stay fully isolated.
</Note>

## Fragments (HTMX / Datastar)

Fragments render a small piece of a template without the full layout — ideal for HTMX partial updates.

Mark a fragment with HTML comments:

```php
<!-- app/views/pages/dashboard.html -->
<?php $this->layout('layouts/base') ?>
<?php $this->start('content') ?>

<!-- @fragment stats_widget -->
<div id="stats">
    <span><?= e($statsValue) ?></span>
</div>
<!-- @end -->

<!-- @fragment user_list -->
<ul>
    <?php foreach ($users as $user): ?>
        <li><?= e($user) ?></li>
    <?php endforeach; ?>
</ul>
<!-- @end -->

<?php $this->end() ?>
```

Request a fragment from the controller:

```php
public function statsWidget(Response $res): Response {
    return $res->fragment('pages/dashboard', ['statsValue' => '42'], 'stats_widget');
}
```

When a fragment is requested, the layout is **bypassed entirely** — only the named fragment is extracted and returned. Much faster than rendering the full page and discarding everything else.

<Warning>
Fragments must be flat — no nesting. The parser throws `ViewException` on nested, unmatched, or unclosed markers.
</Warning>

### Smart View

`Response::smartView()` auto-selects full page or fragment by the request headers (`HX-Target` / `datastar-target`). Use it when one endpoint serves both full-page loads and HTMX partials — pass the current `Request`:

```php
public function dashboard(Request $req, Response $res): Response {
    $data = ['statsValue' => '42', 'users' => ['Alice', 'Bob']];
    return $res->smartView('pages/dashboard', $data, $req);
}
```

## Shared Data

Cross-cutting values like `current_user` or `app_name` can be injected into every template:

```php
// in middleware or boot
View::share('currentUser', $user);
View::share('appName', config('app.name'));
```

Shared data is merged with per-render data; per-render keys win on conflict.

## Best Practices

| Do | Don't |
|----|-------|
| Use `e()` on every output | `<?= $user->name ?>` — XSS risk |
| Use `*Props` objects for components | Array props for complex components (no IDE help) |
| Split HTMX responses into fragments | Render full pages for every partial update |
| Keep fragment markers flat | Nest fragments inside fragments |
| Prefer `.html` extension | Mix `start()` and `section()` in the same file |
| Set `View::share()` in middleware | Pass the same data in every controller |

## Helpers

| Function | Purpose |
|----------|---------|
| `e($value)` | HTML-escape a string |
| `component($name, $props)` | Render an isolated component |
| `componentWithParts($name, $props, $closure)` | Render a component with named parts |
| `part($name, $default)` | Get a named part inside a component |
| `hasPart($name)` | Check if a part exists |
| `route($name, $params)` | Generate a URL for a named route |
| `asset($path)` | Vite-managed asset URL |
